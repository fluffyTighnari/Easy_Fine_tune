# 第 7 步：造训练样本

**产出**：`work/sft/{train,val}.jsonl`、`work/reports/7-build-sft.md`

## 跑

```powershell
cd learn
..\.venv\Scripts\python.exe pipeline\build_sft.py
```

## 样本长什么样

```
[system] 你正在用微信和朋友聊天。
[human]  对方的一次发言（连发多条会合并）
[gpt]    目标人物的一次连发（多条合并）   ← 训练目标
[human]  ...
[gpt]    ...                              ← 只训练 gpt 段
```

改 `config/persona.yaml` 里的 `persona.system_prompt` 就能改 system 段，每条样本都带。

## 规则

| 规则 | 说明 |
|---|---|
| 连发合并 | 连续同角色的消息合成一个 turn —— 他一次「啪啦啪啦发三条」就是一个回复 |
| 超长切块 | 一次连发 > 8 条或 > 300 字，切成多个样本 |
| 上下文 | 往前取 ≤ 3 轮、≤ 600 字，不跨会话；必须从对方发言开始 |
| 排除项 | 第 6 步 `target_ok = false` 的消息不进 target，也不进上下文 |
| 去重 | 完全相同的样本只留一条 |
| 切分 | 按时间，最后 10% 作 val（至少 50 条） |

**为什么合并连发**：他习惯一次发好几条短的。按单条训练，模型会学会「只回一句」；合并后模型学到的是「一次回复几条」这个真实节奏。

## 报告看什么

| 项 | 要判断的 |
|---|---|
| 样本数 | ≥ 300 才能训；几千条比较理想 |
| 跳过：无上下文 | 对话开头那几条没上文，正常 |
| 目标长度 p50 / p90 | 决定模型回复的长短 |
| 整条样本长度 p99 | 第 8 步据此定 `cutoff_len` |
| 目标消息条数分布 | 看他一次发几条 |
| 时间切分 | train 必须全部早于 val |
| 样例 | 抽 3 条确认像人话 |

## 闸门

| 闸门 | 标准 |
|---|---|
| 样本数 | ≥ 300 |
| 每个样本含 system | 全部 |
| 每个样本有人类发言 | 全部 |
| train/val 时间不交叉 | train 最大时间 ≤ val 最小时间 |
| target 非空 | 全部 |

## 配置

```yaml
sft:
  max_context_pairs: 3        # 上下文最多几轮
  max_context_chars: 600      # 上下文总字数上限
  val_ratio: 0.1
  min_val: 50
```

## 出问题怎么办

| 现象 | 处理 |
|---|---|
| 样本数 < 300 | 数据太少，或 `max_context_pairs` 调小让更多样本有上文 |
| 目标长度 p90 太小（<30 字） | 正常，他的回复就是短 |
| 整条样本 p99 接近 max | `max_context_pairs` 调小到 2 |
| 样例里上下文接不上 | `max_context_chars` 太小，调大到 800 |
| val 里出现老数据 | 检查时间戳是否真的升序（第 4 步） |
